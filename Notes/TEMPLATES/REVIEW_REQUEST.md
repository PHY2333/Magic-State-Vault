# 审查对象

审查 Browser 提示所绑定的 GitHub commit 中的完整目标文件。以该 commit 中的实际文件为准，不依据上一轮作者对正文的解释、自评或摘要作出结论。

# 原始目标

见同任务的 `PRO_REQUEST.md`。审查时同时判断目标本身是否在全文中真正实现，而不是只核对若干显式要求是否出现。

# 审查原则

把目标文件视为一篇待发表的完整笔记，从头连续阅读。不要因为某段与上一轮输出一致而默认保留，也不要仅因个人措辞偏好重写已经清楚、准确且连续的内容。

需要判断的是正文能否让目标读者形成可继续使用的理解。

# 审查重点

## 1. 整篇目标与主线

- 开头是否建立了合适的对象、问题或整体图景；
- 全文是否持续服务同一学习目标；
- 各节是否真正推进主线，而不是堆放相关知识；
- 是否存在维护者视角、依赖清单、canonical ownership、任务范围或链接串侵入正文。

## 2. 读者能力与章节连续性

- 每一节实际依赖的知识是否已由原始请求允许，或已在前文建立；
- 前一节的出口是否足以支撑下一节；
- 是否出现突然切回专家压缩、符号密度突增或未经铺垫的高级工具；
- 若某节只解决总问题的一步，是否清楚说明其与总问题的关系，并在适当位置返回主线。

## 3. 定义、术语与对象角色

- 新对象是否在首次承担判断、计算或推导前得到足够说明；
- 定义是否循环、空泛或只用一个陌生术语解释另一个；
- 是否区分概念一般是什么，以及它在当前构造中承担什么作用；
- 工具和高级术语是否在其用途出现后才引入。

## 4. 推理、公式与抽象总结

- 关键公式是否说明对象、条件、映射方向和用途；
- “因为、所以、等价、保证、对应、来自”等结论是否可以沿前文追踪；
- 是否用“显然、自然、容易看出、良定义、相容”等词跳过关键步骤；
- 直觉或概括性句子是否只压缩已经建立的内容；
- 每条抽象总结是否能还原为前文的具体对象、条件、关系和后果；不能还原的句子应重写或删除。

## 5. 解释深度与复杂推导

- 主线所需理由是否充分；
- 上游背景是否被无必要地完整重证；
- 支持性长计算是否压过当前主题；
- 复杂推导是否先给目标、困难或证明地图；
- 选读和补充内容跳过后，主线及后文是否仍成立。

## 6. 一般理论、来源与文件职责

- 一般结论、论文特例、具体实例、参数支线和应用是否清楚区分；
- 来源没有支持的内容是否被补猜或过度一般化；
- 一篇文件是否混入本应独立成为 lesson、derivation 或 paper-guide 的长支线；
- 链接是否只承担进一步阅读，而没有替代当前解释。

## 7. 行文、重复与 Obsidian 渲染

- 中文是否自然、统一，不像计划、审查表或 checklist 的改写；
- 是否存在重复定义、竞争性解释、补丁式段落或无效过渡；
- 标题是否准确反映内容；
- 所有数学是否使用 Obsidian 的 `$...$` 和独立 `$$`；
- 是否存在 `\(...\)`、`\[...\]`、`/(...)`、双重转义或其它无法正常渲染的形式。

# 审查输出

若完整目标文件已经达到原始目标，并且没有需要修改的实质问题，返回：

```text
PRO_STATUS: REVIEW_PASS
```

若存在需要修改的问题：

- 不要只列建议；
- 直接返回所有受影响目标文件的完整修正版；
- 不修改未列入 `target_files` 的文件；
- 保留来源支持、正确公式和已有有效内容；
- 严格遵守 `Notes/PRO_OUTPUT_PROTOCOL.md`；
- 使用 `PRO_STATUS: COMPLETE`；
- 在 `END_RESPONSE` 后不再输出内容。

若无法读取目标文件或完成审查所必需的来源，只返回协议规定的 `NEEDS_CONTEXT`，并准确列出缺失路径；不得根据旧对话内容补猜。
